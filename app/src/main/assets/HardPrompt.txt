### Search and text-entry rules

Use the tools actually listed in available_tools. tap_by_text is valid for navigating to a Search tab before an editable search field exists. Its name is tap_by_text, never tap_by_name.

Follow this workflow:

1. Inspect the latest actual UI tree. Reuse a fresh, usable observation rather than requesting it again.
2. Identify the search field using the current UI tree, app context, and any visible text, hint, description, or nearby label.
3. If Search is a navigation tab/button rather than an editable input, tap that actual control first and verify the resulting screen. Then use `type_into_field_near` to locate the relevant editable field and enter the user's exact search query.
   - Some apps have two activation stages: the Search tab opens a page with a non-editable search placeholder. Tap that observed placeholder and observe again. Do not type until a visible editable=true input exists.
   - Set `query` to a label, hint, text, or content-description that identifies the search field or nearby UI element.
   - Set `text` to the exact query the user wants to search for.
   - Do not assume the field must contain the word "search".
   - Do not invent a label or field that is not supported by the current UI observation.
4. If `type_into_field_near` cannot reliably identify the field, inspect the UI tree again. If necessary, use `tap` with coordinates grounded in the latest UI tree to focus the field, then use `type_text` to enter the query.
5. Call `press_enter` when appropriate to submit the search.
6. Call `get_ui_tree` again to inspect the results and verify that the requested content was found.

Never select a different tool merely because it is easier. Never claim that a search succeeded without observing its results.
For duplicate labels (such as Search), use an observed view_id or bounds with tap_by_text, or an actual coordinate tap. Do not choose an input when the goal is the navigation tab. On a fresh observation showing that an accessibility click failed, retry with prefer_gesture=true and a recovery_reason, within limits.
For navigation taps supply expected_ui describing the destination; selected_text verifies that a tab is selected rather than merely visible. Verify typed text before submission; press_enter only if the focused control supports it, otherwise tap an observed submit button. Verify song title and playback state before claiming a song is playing.
Swipe directions describe finger movement: left x1>x2; right x1<x2; up y1>y2; down y1<y2. Use screen dimensions and the intended scrollable container's bounds, away from system gesture edges. A delivered gesture may leave content unchanged at a boundary; report that honestly and do not invent movement.
